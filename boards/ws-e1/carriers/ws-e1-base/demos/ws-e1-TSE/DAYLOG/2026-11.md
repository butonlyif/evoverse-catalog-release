## 2026-11-02 TSE 千兆以太网工程（ws_e1_tse）

### 修复的真实 bug

1. **rx_axis_mac_tready 背压违反 TSEMAC UG**（rtl/eth_pkt_fifo.v、rtl/mac_rx2tx.v）
   UG v6.3 L415：RX 背压不支持，帧中拉低会静默损坏帧。改为 tready 恒 1 +
   SOF 帧粒度准入（FRAME_GUARD=1536 字，放不下整帧则整帧丢弃）+ 溢出 sticky
   （toggle CDC 到 APB 域）。tb_eth_pkt_fifo / tb_reg_pkt 同步重写，仿真全 PASS。

2. **tx_free_cnt 12 位溢出截断**（rtl/eth_pkt_fifo.v L219、rtl/reg_apb3.v 'h092、
   driver/efx_tse_mac.h MacTxSend）
   `FIFO_DEPTH[11:0] - wrcnt`：DEPTH=4096=2^12，FIFO 空时 free 读数 4096 截断
   为 0x000。固件 MacTxSend 判 `free < len` 永远成立 → 固件卡死（板上 UART
   停在 "TX tick" 行的直接原因）。修复：tx_free_cnt 扩 13 位（空=4096 可表示），
   TX_STATUS 位域 [12:0] free + [13] full，固件掩码改 0x1FFF。tb 断言同步修正
   （旧断言 `12'd4096` 同源截断，一直在测 0）。

3. **顶层 8 个 eth_* 信号隐式 1 位 wire 截断**（rtl/ws_e1_tse.v）
   eth_rx_word_cnt[11:0]/eth_tx_free_cnt[12:0]/eth_rx_rddata[9:0]/eth_tx_wrdata[8:0]
   等只有端口连接、无 wire 声明 → 隐式 1 位 wire 截断 → RX_STATUS/TX_STATUS
   读数全部不可信（之前所有 "RX=0" 读数存疑）。已补显式声明。

4. **axis 时钟 50M 违反手册 Table 5**（rtl/ws_e1_tse.v L210）
   1G @ AXIS 8bit 要求 ≥125MHz，原接 clk(50M) 上限仅 400Mbps。改接 clk_125m
   （官方注释原话："In full throughput usecase ... should be set to 125Mhz"）。
   pnr PASS，slack +4.06ns。

### 联合仿真 tb_sw_path（sw 帧 + MAC，2026-11-02 晚）

- 动机：用户建议"你的逻辑加上 MAC 做仿真"，判定 sw 帧→MAC 消费在逻辑层是否成立。
- 架构：sim/tb_sw_path.v 例化 ws_e1_tse（SIM_MODE：SoC 缺位、apb3_* 提升为顶层
  端口由 tb 驱动）+ APB BFM 逐行复刻固件 TEST_MODE=2 SwEchoRun 序列（RMW 设
  promis、MacAddrSet(0,0)、广播过滤关、CntClean、MacTxSend 逐字节写 0x24C 末字节
  tlast）+ 判据 aFramesTxOK/RGMII ctl 帧计数。加密 IP 用非加密仿真模型
  ip/mytse/Testbench/modelsim/mytse.sv。
- **首跑复现板上现象（假象）**：tx_beat=318（3×106 全被 MAC AXIS 吃掉、tready 恒 1、
  free=4096 排空），但 ctl_frames=0、aFramesTxOK=X → MAC 收帧不发送、统计 X。
- 根因 = **仿真复位工件**：顶层 `mac_reset = ~pll_0_locked` 是组合逻辑，板上 PLL
  上电数百 ms 后才锁定（locked=0 期间 MAC 正确复位）；tb 原把 locked 从 t=0 拉高
  → MAC 从未复位 → TX 引擎 FSM 为 X。修复：tb 模拟锁定（#200 后拉高）。
- **修复后 PASS**：`aFramesTxOK=3  tx_beat=318  ctl_frames=3  TX_STATUS=00001000`
  → sw 帧→mux3→MAC→RGMII 逻辑层全通，自研 RTL 无 bug。
- **板上"MAC 不消费 sw 帧"根因闭环**：tx_free_cnt 12 位溢出 bug → 固件 MacTxSend
  死循环（free<len 永真）→ 帧从未完整写入 FIFO → MAC 无帧可发。此前实验 D/E
  （归因 ena 序列/proto_reset 脉冲）均在该 bug 未修时进行，结论作废。
- 附带修正：reg_apb3.v 'h092 读数拼接 19'h0+1+13=33 位（MSB 溢出，凑巧无功能
  影响）→ 改 18'h0。

### 板上 free 读数硅级失效定位与编码修复（2026-11-02 晚，第二轮）

- 板级探针（OpenOCD，sw/diag_tx2.cfg / diag_pat2.cfg）：
  - MUX=0x10、CMD=0x00040013：固件正常跑到 sw 模式
  - TX_STATUS 恒读 0x2000、aFramesTxOK=0、RX 全零
  - **修正探针教训**：mux3 映射 00=pattern / 01=rx2tx 回环 / 1x=sw（axi4_st_mux3.v
    L485 注释）。首版探针误写 MUX=0x1 选了回环路（RX 死→无输出），得出"TX 引擎死"
    的**错误结论**；改 MUX=0x0（PatGen 同款）后 aFramesTxOK=2 → MAC TX 引擎正常。
- 板上 TX_STATUS=0x2000 的唯一自洽解释：free[12]=0 + free[11:0]=0 + bit13 幻影 1
  → **wrcnt=0（固件一个字节都没写）+ free 的 bit12（"4096 空闲"位）在硅里丢失**。
  固件第一次 MacTxSend 读到 free=0（<106）即挂死。RTL 仿真同样状态读 0x1000 正确
  → 硅逻辑≠RTL。0x2000 在两个 bit（18:43 旧顶层混编 bit / 20:10 一致 bit）上相同
  → 该算术模式（13 位常数 4096 − 12 位值 + ==0 比较）综合产出硅级错误。
- 附带发现：RTL 仿真中 clk_50m 曾用 100MHz 加速，掩盖真实 50M/125M 时钟比——
  改回真实 50MHz 后联合仿真仍 3/3 PASS，时钟比假设排除。
- 网表取证：outflow/ws_e1_tse.map.v 中 'h092 bit13 是"保持型 mux"（几乎恒 1，
  幻影 bit13）、'h092 bit12 的 NAND4 形态与 RTL 语义（~|wrcnt）不符；加密
  protected_cell（MAC 内核容器）阻断全量网表仿真，LUT 级手工追踪到 bit12/13。
- **编码修复（釜底抽薪，eth_pkt_fifo.v/reg_apb3.v/ws_e1_tse.v）**：
  `tx_free_cnt = tx_wrfull ? 0 : (13'd4095 - fill)`（全 12 位算术，无 2^12 常数
  边界）+ 新增 `tx_full` 输出直通 FIFO 真满标志；TX_STATUS=[13]=tx_full、
  [12:0]=free（空=4095）。固件掩码 0x1FFF 不变。
- 修复后回归：tb_eth_pkt_fifo / tb_reg_pkt 全 PASS；tb_sw_path（真实 50M/125M）
  3/3 帧消费，TX_STATUS=0x00000fff ✓。

### 根因链（3 轮编译迭代）
1. **viewer 按键路由**：selecting 状态下数字键 0-3 判断排在截屏('3')/toggle('1')

2. **图案模式下 ARP 应答上不了线（结构性）**：TX mux 指向图案发生器，CPU 应答帧

   ARP 解析 → 控制 UDP 从未发出 → 板子从未收到任何 PAT MODE 命令。
3. **mux 注入三连修**（固件 PatCtrlRun）：
   - v1 mid-frame 直接切 mux：MAC 只认 tlast 分帧，半截图案帧与应答拼成巨帧丢弃

     恒 0 → 等待恒真立即通过）→ 等效 v1；
   - v3 地址修正：轮询 pat_dbg（TSEMAC_CSR+0x24C，bit[5:3]=state）等 S_IDLE
     （帧间空闲≈12ms，sw 帧发送≈12µs）再切 mux 注入、发完切回。
   - 教训：RTL 寄存器名('h093) ≠ 固件地址(0x24C=0x24C>>2 映射)，未定义 CSR 读
     恒 0 会把轮询等待静默变空转。

**第一步 tb_sw_path 回放（区分 RTL vs 硅）**：重建 Questa 工程（work_kill 库；

**第二步 map.v 网表取证（DC_FIFO TX 实例 u_eth_pkt_fifo/u_tx_fifo）**：
- 写口 cone LUTMASK 逐一解码（efx_lut4.v 权威语义：LUTMASK=16bit 真值表，
  lutrom[{I3,I2,I1,I0}]）：n46 = ~eth_tx_full & loc_wr_vld & addr_match('h093)

- **根因**：DC_FIFO 复位握手 `WrClkRstGen[1] <= &RdClkRstGen`（跨域双向，
  初值 2'h3）的两个 [1] FF 被 map **消解为无驱动 wire**（[1] 复位释放后终态
  恒 0，综合视为死寄存器；u_rx_fifo 同款 FF 却保留——综合处理不一致）。
  下游全部写/读域寄存器（FullFlag/FifoWrAddr/WrRdAddr/RdAddrChg…）的 SR 配
  **SR_POLARITY=1'b0（低有效，efx_ff.v L67 权威语义 sr_int=~SR）**直连该
  wire → 硅上 wire=0 → sr_int≡1 **恒异步复位**。
- 板上读数 100% 吻合：FullFlag 恒 0（TXSTAT bit13=0 ✓）、FifoWrAddr 恒 0
  （写地址不推进）、wrcnt=WrAddrDiff 恒 0 ✓、free 恒 4095 ✓、读域恒空 →
  tvalid 恒 0 → TX 不发 ✓。CPU 写 strobe（n46 正确）被恒复位吞掉：数据反复
  覆写 BRAM 地址 0，永不下发。定性：**Efinity map 阶段硅级病灶，11-02 病灶
  家族近亲（同 DC_FIFO 计数/复位逻辑、同 RTL≠硅）**。

### 根因 1（PC 端）：raw10.py _meta_mode→相机切换漏置 _pending（G11n15 设计缺陷）

- 用户重启后仍 fps=0 + 帧号涨 + 丢帧 0：路径 = 控制台先在图案流建立 _meta_mode → 切相机 → 帧首包数据段头命中魔数 → 切出 meta_mode 但 **_pending 未置 True** → buf 凑过 2,592,000B 又触发"超帧长无魔数"判回 meta_mode → 无限振荡回 legacy；legacy 按 (fn,off) 重组相机流因帧首短包（occ=1/2 竞争包）off 与实际字节位置错开 → 永不成帧。fn 来自 meta 每帧 +1 无跳变 → "帧号涨/丢帧 0/fps=0" 画像精确吻合。
- 修复（doc/pc_tools/raw10.py feed()）：切换路径补 `self._pending = True`（魔数已消费，开始字节计数）。
- 验证：合成图案流→真实相机流→回切图案三阶段回放：切相机后 57 完整帧 ✓（修复前该场景 0 帧）；图案侧模式判定税牺牲首帧为已知行为，连续流自愈。

### 根因 2（FPGA 端）：gen S_IPG 卡死 → 切不过图案（G11n15 纯流式次生缺陷）

- G11n15 纯流式使 FIFO 帧间隙排空到 0 → occ_ready=0 → cam_pkt_go=0；gen 包间停 S_IPG，退出条件 `ipg_exit = ipg_cnt>=ipg_lim && (!cam_r || cam_pkt_go)` 永不满足 → 卡死 S_IPG → start_pulse 进不来 → 图案/其它模式启动不了。G11n14 门限时代 occ_ready 恒 1 掩盖了该路径。

## 2026-11-08 G11n16d 后续：换卡后 viewer 仍"画面冻结"根因 = raw10.py FrameReassembler 双 bug（PC 工具）

### 现象与定位

- ASIX 网卡满速验收后用户复测：viewer 画面冻结。probe_reasm.py（viewer 同款
  FrameReassembler 喂真实流）复现：6s 仅 3 完整帧（0.50 fps）、buf 卡 362,950、
  假魔数间隔仅 70/64 包；同期 NDIS 640 Mbps 满速 → 线上数据健康，根因在重组器。

### 双 bug（doc/pc_tools/raw10.py FrameReassembler.feed）

1. **凑帧中仍搜索魔数 → 假魔数切碎帧**：帧界魔数 = FF×5+00×5，恰为 4 白像素
   紧跟 4 黑像素——棋盘格（'3'）每个黑白块边界、相机高光/暗场边缘天然构成该
   序列。pending 态每包 `buf.find(MAGIC)` 命中帧内伪魔数 → 整帧切碎成短帧、
   字节计数清零 → 永远凑不满 2,592,000 → 冻结。
2. **全缓冲 find O(N)/包 → 收包循环被纯 CPU 拖垮**：非 pending 态每包对最大
   2.6MB 缓冲全量扫描，53.7K pps 下实测收包循环仅 8.2K pps（NDIS 同期满速），
   内核缓冲溢出丢 5/6。

### 修复（同文件 feed，附带增量扫描游标 `self._scanned`）

- pending 态纯字节计数凑帧（RTL 帧长精确保证），完全不搜魔数；凑满即出帧。
- 非 pending 态增量搜索：只扫新到字节（`find(MAGIC, scanned-9)` 9B 重叠防
  跨包魔数漏检），命中后游标归零；meta_mode 两处转换同步清游标。
- 丢包自愈语义保持：pending 中丢包 → 错位处计数达帧长 → 发 1 帧底部花屏
  "完整帧" → 下一帧增量搜索重对齐，无需额外 overflow guard。

  buf 残 5B、n_dups=0、n_resync=0。

## 2026-11-08 G11n16d 后续：相机偏紫根因 = 无白平衡（非拜耳相位错，G11h-4 备忘闭环）

### 现象

- 模式切换修复后用户复测：图案四模式颜色全部正常，相机画面整体偏紫。

### 定位（抓帧 2x2 CFA 子平面统计）

- 相机帧四位置均值：[0,0]=85.4 / [0,1]=70.1 / [1,0]=72.3 / [1,1]=85.3。
  按 RGGB 解码即 R=B≈85 > G≈71，品红偏色（R/G=B/G=1.201，完全对称）。
- 曾疑 CFA 相位错（G 在主对角线假设）：但主对角线两位置按 RGGB 应为 R/B
  两通道，均值 0.1% 相等恰是"中性场景 + 对称品红偏色"的画像；且若是相位
  错，修正后应显绿色主导而非用户所见紫色——显示观察与统计均自洽于白平衡
  假设，唯一可判别的是外部真值。
- **权威真值**：catalog 参考工程 ws-e1-cam-ddr-csi2-demo（同款 IMX415，
  板级标定"上电即出像"）apb_cam_ctrl 默认 phase=0 (RGGB)、wb_r/g/b=
  200/235/180（R、B 增益低于 G——正是补偿 G 缺乏的品红偏色）。
  **拜耳相位确认 RGGB 无误，G11h-4"重定拜耳排列"备忘就此闭环**（G11n15
  时代的"空间异色"系帧失步伪影，不构成相位证据）。

### 根因与处置

- 根因：IMX415 裸传感器（无 IR-cut）近红外泄漏 + 光源光谱 → R/B 响应比 G
  高 20%，viewer 相机模式默认增益全 1.0 无白平衡。图案流为合成数据通道
  天生均衡，故只有相机偏紫。
- 处置：相机模式加 `--wb 1.0,1.2,1.2,1.0`（R,Gr,Gb,B），板测 R/G=B/G
  1.201 → 1.021 基本全平衡。增益定标记录于 raw10_viewer.py docstring；
  换光照环境按灰世界重配。若偏色随场景剧变，考虑模组加 IR-cut 滤光片。

### 自动白平衡（--autowb，用户选择）

- raw10_viewer.py 新增 auto_gains()：每帧算 4 个 CFA 子平面均值，归一到总
  均值（灰世界），指数平滑 0.1/帧（~0.3s 收敛）防闪烁，增益限幅 0.25..4.0
  防黑帧发散；OSD 实时显示当前增益。--wb 初值仍可作为收敛起点。
- 板测（真实相机流喂 viewer 同款循环）：frame1 R/G=1.185 → frame30
  R/G=B/G≈1.016，29.83 fps 无性能回退。

## G11n17 CFA 相位定案 + 相机显示链（2026-11-08）

**背景**：相机模式偏紫 → 加 --autowb + --gamma 2.2 显示编码后草地仍显示紫色
（用户板测报告）——草地呈补色是真 G 被解码进 R/B 平面的决定性证据，推翻
2026-11-06 "CFA 相位确认无误" 的结论。

**判据链（三重板测验证）**：
- RGGB 解码下白灯 R/G≈1.64（典型索尼传感器 G 通道 QE 最高，R 高 64% 不合理）
- 2x2 子平面统计：主对角线均值高 20%（真 G 落主对角线）
- 草地紫色、红色物体显紫；--cfa GRBG 下草地绿/白灯白/红色显红（用户板测确认）

**定案**：本板相机流真实相位 = GRBG。RTL 合成图案流仍为 RGGB（raw10_pat_src
行偶 {R,Gr}），两流共用同一条 FIFO→UDP→viewer 链路，打包/解包顺序经彩条 +
expected_image 数值比对双重验证无误 → 差异属传感器流本身，非 RTL bug。

**参考工程误标教训**：ws-e1-cam-4K-1080-60fps-ref 的 userDef.h 标注"IMX415
标定 0(RGGB)"不可信——其 wb_design_spec 自载"200/235/180 板级实证画面发绿"
（往下压 R/B 的增益只在相位错时才"看起来合理"，压过头=发绿），其标定从未
真正成功。勿再以该注释为相位依据。

**落地修改**：
- raw10_viewer.py：--cfa 默认 RGGB→GRBG（看图案需显式 --cfa RGGB）；
  --wb 默认 1.22,1.0,1.0,1.18（GRBG 相位对白灯定标：R=G均值/R均值=85.3/70.1，
  B=85.3/72.3）；--gamma 2.2 默认（sRGB 显示编码，暗部提亮高光不动，解决
  灯过曝+黑圈压黑）；--autowb 保留（单色主导场景灰世界失效时用手动 WB）。
- tse_console.py：--cfa 默认同步 GRBG。
- 语法检查两文件 PASS。

**传感器增益链**（同日）：SHR0=8 已无曝光余量 → imx415_rom.sv GAIN_PCG_0
（0x3090）追加 8'd142: 0x3C=+18dB（值=dB×10/3，上限 0xF0=72dB；≤30dB 模拟
区 SNR 优）。用户自编译烧录 +18dB 后亮度 ×8、偏色随之大幅缓解（紫主要来自
低照度通道失衡而非缺 IR-cut——前期误诊一并更正）。

**AWB 重做（同日续）**：GRBG 默认相位落地后发现旧 auto_gains 按固定 RGGB
位置取均值，与 apply_wb 的 CFA 映射施增益错位——--autowb 在 GRBG 下已失效。
重做为中性亮块法（合成数据三场景验证 ALL PASS）：
- raw10.py 抽出 cfa_channel_map()（Gr/Gb 按 Sony 约定归属），apply_wb 与
  auto_gains 共用，算/施同源；
- auto_gains 主判据：2x2 块亮度 85 分位 + 非饱和(<1010) + 当前增益折算后
  块内 |max-min|<=20%（色度筛掉亮草等彩色高亮——白块可能仅占 3%，纯亮度
  分位会被亮草淹没，首轮实测即踩中）；中性亮块 <1% 回退全图灰世界；
- 锚定最亮通道（target=max(means)）：只补短不压长，白块/灯保持原亮度
  （锚全图均值会把它拖暗到场景均值，首轮实测即踩中）；
- 通道归属随 --cfa，EMA 0.1/帧，限幅 0.25..4.0。
- 板测判据：灯白、草地绿、红物红； OSD awb 行增益应稳定在 ~1.2 量级。
- viewer 显示竖纹/锯齿排查：raw 抓帧 FFT 实证数据无列纹（2~64px 周期幅值≈0，
  even/odd 差 0.11 LSB）→ 定位 Windows HighGUI 不感知 DPI 的位图拉伸摩尔纹；
  raw10_viewer.py 启动加 SetProcessDpiAwareness(2)（窗口创建前），1:1 即物理像素。
- 暗场竖纹定案：列 FPN 静态（帧间列剖面相关 0.997），暗场+gamma 提亮显形、
  亮场被信号淹没（两态抓帧对比）；viewer 加逐帧列校正 decol_columns()
  （列中位剖面-去>32px 慢变-限幅±12LSB，隔4行采样 ~5ms），--decol 0 可关。
- G11n17 锯齿根因定案：相机流 40bit 组内像素反序（raw_2_axi4st 字段序与

## G11n17 计算摄影增强：TNR + CLAHE（2026-11-08）

**背景**：用户降增益至 0x14(+6dB) 后反馈"比 0x28 好，但还是没手机相机清楚，
画面也暗"。曝光已无余量（SHR0=8 拉满，imx415_rom.sv L13 注释），增益 0x14
已很低——传感器侧杠杆用尽，画质差距只能靠显示端计算摄影补。手机相机"清楚
又亮"的来源是多帧降噪 + 局部色调映射，viewer 用最小实现近似。

**灯环定案修正**（终版，推翻"饱和 bloom"初判）：径向亮度剖面单调衰减、
数据中不存在暗环凹陷；环区（r130-170px，亮度 250-400）比墙（110-160）还亮
2 倍 = veiling glare（镜头内散射把环区垫起）。降增益只能等比缩小眩光，
物理上不可消；可选算法补偿 --deflare 已提出未确认。

**raw10_viewer.py 新增**：
- `--tnr N`：时域降噪。bayer uint16 域 EMA 累加（cv2.accumulateWeighted，
  alpha=1/N，单 float32 缓冲，无环形队列），N 帧平均 SNR +√N；置于管线
  最前（AWB/列校正统计随之更稳）。代价：运动物体 ~N/30s 拖影，静态机位
  可忽略。
- `--tone`：CLAHE 局部色调映射。gamma 后显示图 LAB L 通道（保色彩），
  clipLimit 2.5 / 8x8 tiles——全局 gamma 整帧统一提亮，阴影里还是黑；
  CLAHE 按局部块重分布，暗部亮起来高光不炸。
- 管线顺序：bayer → TNR → decol → AWB/WB → demosaic(EA) → gamma → CLAHE
  → 显示。两项均 opt-in，OSD 显示 `enhance:` 行确认生效。
- py_compile PASS；临时探针 probe_full.py 及分析 PNG 已清理。

**板测建议**：`uv run raw10_viewer.py --tnr 6 --tone`——噪点应明显变细、
暗处细节显形（TNR），灯周围/阴影层次变亮（tone）。运动拖影明显则降
--tnr 4 或 2。

**v2 重做（用户否决 v1 四连：卡顿/拖影/发灰/花斑）**：TNR 改运动自适应
EMA（与上帧差 >24LSB 的像素直接采用本帧，静止区平均、运动区无拖影）；
CLAHE 改增益图法（1/4 分辨率 CLAHE → gain=eq/small 下限 1.0 上限 3.0，
双线性上采样后 RGB 同乘——无块边界、不发灰、只提亮不压高光）。分段基准
实测（本机）：tnr 17ms + decol 20ms + demosaic 1.4ms + gamma 14.5ms +
tone 52ms ≈ 106ms，远超 33ms 帧预算——卡顿主因证实，v2 tone 已压缩，
未再整体基准（用户叫停，改走轻量路线）。
- 随后用户板测：gamma 2.2 接受；红色不够红 → 加 --sat（HSV S 通道乘
  系数，gamma 提亮暗值显粉的补偿），建议 1.2~1.4。
- 用户问 WB 与亮度关系 → 澄清：WB 管通道比例不管亮度；板端曝光/增益
  固定（无 AE），画面亮度不随构图（有无灯）变化。加 --ev 数字增益曝光
  补偿（单位 stop，×2^ev 折进 gamma LUT，运行时零开销，高光提前饱和）。
- 用户反馈 --ev 提亮后"像没对焦" → 根因是数字增益放大读出噪声 + 压局部
  对比（非真失焦）。加 --sharp（unsharp mask，sigma 1.5，0.5~1.0）补回
  边缘对比；若本来就糊，M12 镜头可机械对焦。
- AWB v3 场景自适应路由（用户选定方案二）：白块法（中性亮块>=1%）为主，
  不足回落 Shades of Grey p=6（Minkowski 范数，p=1 退化灰世界、p→∞ 退化
  白块；隔行采样省一半幂运算）——替换灰世界回退，单色主导场景不再把场景
  色当光源。--awb-mode auto|patch|shade 可锁算法；OSD 显示 awb[patch/shade]
  当前估计器。合成场景冒烟测试 PASS（白灯→patch、草地满屏→shade、强制
  patch 失败正确回落 shade）。
- CCM 3x3 上线：--ccm "9 数"或 "imx415" 经验矩阵（未标定），线性域施加

  通道串扰。uint16 饱和 65535 而 gamma LUT 只收 0..1023 → 变换后必须
  np.minimum 回 10bit（数值验证 900/300/200 → 1400/195/95 确认越界真实
  存在）。正式标定需 24 色卡，待用户提供后写回归脚本。
