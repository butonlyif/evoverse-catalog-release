# 2026-11

## 2026-11-02 TSE Gigabit Ethernet project (ws_e1_tse)

### Real bugs that were fixed

1. **rx_axis_mac_tready backpressure violates TSEMAC UG** (rtl/eth_pkt_fifo.v, rtl/mac_rx2tx.v)
   UG v6.3 L415: RX backpressure is not supported, and pulling it low inside a frame
   silently corrupts frames. Changed to tready tied high + frame-granularity admission
   at SOF (FRAME_GUARD=1536 words; if a whole frame does not fit, drop the whole frame)
   + overflow sticky bit (toggle CDC into the APB domain). tb_eth_pkt_fifo / tb_reg_pkt
   rewritten accordingly, simulation fully PASS.

2. **tx_free_cnt 12-bit overflow truncation** (rtl/eth_pkt_fifo.v L219, rtl/reg_apb3.v 'h092,
   driver/efx_tse_mac.h MacTxSend)
   `FIFO_DEPTH[11:0] - wrcnt`: DEPTH=4096=2^12, so when the FIFO is empty the free
   reading 4096 is truncated to 0x000. Firmware MacTxSend then always evaluates
   `free < len` as true → firmware deadlock (the direct cause of the board UART
   stopping at the "TX tick" line). Fix: widen tx_free_cnt to 13 bits (4096 representable
   when empty), TX_STATUS bit fields [12:0] free + [13] full, firmware mask changed to
   0x1FFF. Testbench assertions fixed in step (the old assertion `12'd4096` had the same
   truncation origin and had always been measuring 0).

3. **8 top-level eth_* signals implicitly truncated to 1-bit wires** (rtl/ws_e1_tse.v)
   eth_rx_word_cnt[11:0]/eth_tx_free_cnt[12:0]/eth_rx_rddata[9:0]/eth_tx_wrdata[8:0]
   etc. had only port connections and no wire declaration → implicit 1-bit wire
   truncation → all RX_STATUS/TX_STATUS readings were untrustworthy (every previous
   "RX=0" reading is now in doubt). Explicit declarations added.

4. **axis clock 50M violates the manual Table 5** (rtl/ws_e1_tse.v L210)
   1G @ AXIS 8bit requires ≥125MHz; connecting to clk(50M) caps throughput at only
   400Mbps. Reconnected to clk_125m (official comment verbatim: "In full throughput
   usecase ... should be set to 125Mhz"). pnr PASS, slack +4.06ns.

### Joint simulation tb_sw_path (sw frames + MAC, evening of 2026-11-02)

- Motivation: the user suggested "add the MAC to your logic and simulate", to determine
  whether sw frame → MAC consumption holds at the logic level.
- Architecture: sim/tb_sw_path.v instantiates ws_e1_tse (SIM_MODE: SoC absent, apb3_*
  promoted to top-level ports driven by the tb) + an APB BFM that replicates the firmware
  TEST_MODE=2 SwEchoRun sequence line by line (RMW set promis, MacAddrSet(0,0), broadcast
  filter off, CntClean, MacTxSend writing 0x24C byte by byte with tlast on the last
  byte) + judgement criteria aFramesTxOK/RGMII ctl frame counters. The encrypted IP
  uses the non-encrypted simulation model ip/mytse/Testbench/modelsim/mytse.sv.
- **First run reproduced the board phenomenon (an illusion)**: tx_beat=318 (3×106 all
  swallowed by the MAC AXIS, tready tied high, free=4096 drained), but ctl_frames=0,
  aFramesTxOK=X → the MAC received frames but did not transmit, and the statistics were X.
- Root cause = **simulation reset artifact**: the top-level `mac_reset = ~pll_0_locked` is
  combinational; on the board the PLL only locks hundreds of ms after power-up (during
  locked=0 the MAC is correctly reset); the tb instead raised locked from t=0 → the MAC
  was never reset → the TX engine FSM was X. Fix: the tb simulates lock (pulled high
  after #200).
- **PASS after the fix**: `aFramesTxOK=3  tx_beat=318  ctl_frames=3  TX_STATUS=00001000`
  → sw frame → mux3 → MAC → RGMII is fully working at the logic level; the in-house RTL
  has no bug.
- **Closed loop on the board's "MAC does not consume sw frames" root cause**: the
  tx_free_cnt 12-bit overflow bug → firmware MacTxSend infinite loop (free<len always
  true) → the frame was never completely written into the FIFO → the MAC had no frame to
  send. The earlier experiments D/E (attributing the fault to the ena sequence /
  proto_reset pulse) were all performed while this bug was unfixed, so those conclusions
  are void.
- Incidental correction: reg_apb3.v 'h092 read value concatenated 19'h0+1+13=33 bits (MSB
  overflow, coincidentally with no functional impact) → changed to 18'h0.

### Locating the silicon-level failure of the on-board free reading and the coding fix (evening of 2026-11-02, second round)

- Board-level probes (OpenOCD, sw/diag_tx2.cfg / diag_pat2.cfg):
  - MUX=0x10, CMD=0x00040013: the firmware runs normally up to the sw mode
  - TX_STATUS constantly reads 0x2000, aFramesTxOK=0, RX all zero
  - **Probe correction lesson**: mux3 mapping is 00=pattern / 01=rx2tx loopback / 1x=sw
    (axi4_st_mux3.v L485 comment). The first version of the probe wrongly wrote MUX=0x1
    and selected the loopback path (RX dead → no output), producing the **wrong
    conclusion** "the TX engine is dead"; after switching to MUX=0x0 (same as PatGen),
    aFramesTxOK=2 → the MAC TX engine is normal.
- The only self-consistent explanation for on-board TX_STATUS=0x2000: free[12]=0 +
  free[11:0]=0 + a phantom bit13 of 1 → **wrcnt=0 (the firmware never wrote a single
  byte) + the free bit12 ("4096 free" bit) is lost in silicon**. The firmware's first
  MacTxSend read free=0 (<106) and hung immediately. The same state in RTL simulation
  reads 0x1000 correctly → silicon logic ≠ RTL. 0x2000 is identical on two bits
  (18:43 old top-level mixed-coding bit / 20:10 consistent bit) → this arithmetic
  pattern (13-bit constant 4096 − 12-bit value + ==0 comparison) synthesizes into a
  silicon-level error.
- Incidental finding: in RTL simulation clk_50m had been accelerated to 100MHz, masking
  the real 50M/125M clock ratio — after restoring the real 50MHz the joint simulation is
  still 3/3 PASS, so the clock-ratio hypothesis is excluded.
- Netlist forensics: in outflow/ws_e1_tse.map.v 'h092 bit13 is a "hold-type mux" (almost
  constantly 1, phantom bit13), and the NAND4 shape of 'h092 bit12 does not match the
  RTL semantics (~|wrcnt); the encrypted protected_cell (the MAC kernel container)
  blocks full netlist simulation, so manual LUT-level tracing reached bit12/13.
- **Coding fix (root-cause elimination, eth_pkt_fifo.v/reg_apb3.v/ws_e1_tse.v)**:
  `tx_free_cnt = tx_wrfull ? 0 : (13'd4095 - fill)` (full 12-bit arithmetic, no 2^12
  constant boundary) + a new `tx_full` output wired straight to the FIFO's true-full
  flag; TX_STATUS=[13]=tx_full, [12:0]=free (empty=4095). The firmware mask stays 0x1FFF.
- Regression after the fix: tb_eth_pkt_fifo / tb_reg_pkt fully PASS; tb_sw_path (real
  50M/125M) consumes 3/3 frames, TX_STATUS=0x00000fff ✓.

## 2026-11-04 RX root cause redirected: PHY driver porting (user instruction: RXC does not toggle, suspect the PHY is not configured)

### Conclusions from a three-way comparison of reference project drivers

- Nantech demo (TJ180A484_TSE): RTL8211F driver + PHY internal loopback demo — a
  different PHY model, the RTL8211F resets with RXC output by default, no reference
  value.
- The project where LOOPBACK was made to work: yt8531fd.h (ported from Linux
  motorcomm.c) — YT8531 is the correct answer.
- Ours: efx_tse_phy.h is already a YT8531 revision but sits in a commented-out BISECT
  state, all key writes are disabled, and PhyNormalInit never calls yt8531_rgmii_init;
  SwEchoRun temporarily did an RMW on bits the reference never touches (0xA001 bit6
  En_ldo, 0x0C bit15).
- Most suspicious: 0xA001 bits2:0 chip mode (UTP_TO_RGMII) was never set — this bit
  controls UTP data → RGMII port routing; if the strap is not 0, RXC will not come out
  no matter how good the link is.
- Clarification of a contradiction in the driver comments: "soft reset breaks the 1G DSP"
  is actually a secondary phenomenon of soft resetting while the chip mode is
  unconfigured; the reference driver soft-resets after the ext configuration + settle
  150ms and was measured to work.

### Porting changes (all complete, firmware compiled PASS 12640B)

1. driver/yt8531fd.h: copied in from the LOOPBACK project, porting macros added
   (PHY_ADDR=0, TSE_Speed_* 0x04/0x02/0x01; this project has no
   efx_tse_userdef.h).
2. main.c: include changed to yt8531fd.h (it conflicts with the Phy_Rd/Phy_Wr
   redefinitions in efx_tse_phy.h, the two cannot be included together); main() switched
   to the reference sequence: yt8531_drv_init → yt8531_drv_linkup (waits for the real
   link, cross-verified via BMSR/SSR) → yt8531_post_link_rgmii → wait for the RXC PLL
   lock (CSR+0x254 bit0, 60s timeout; note that in the current bitstream pll_rgmii locks
   the 50M crystal and is constantly 1, a false pass — it becomes real only after the
   FPGA-side RXC→PLL rework); PhyLoopInit re-enabled (TEST_MODE=1); SwEchoRun drops the
   old diag/RXCK RMW experiments and instead prints an extended register snapshot.
3. tseDemo.h: TEST_MODE 0→2 (RX verification echo mode).

## 2026-11-05 RX path investigation closed: G1 bidirectional loop PASS

### Root cause chain (proven on the board)

The root cause of RXC not toggling = missing configuration in the firmware-layer YT8531
driver, not the FPGA / pins / hardware:
1. 0xA001 bits2:0 chip mode (UTP_TO_RGMII) was never set — UTP data → RGMII port routing
2. 0x0C bit12 RXC gating was never cleared (the PHY stops RXC when there is no link)
3. It never waits for a real link (BMSR/SSR cross-verification), so the diagnostics ran
   under a false link

Evidence: after porting yt8531fd.h (the motorcomm model) from the project where
LOOPBACK was proven to work, the UART shows a real link at 1000M full
(SSR=0xbc40/BMSR=0x796d/ANLPAR=0xcde1/STAT100=0x3800), GATING=0x8000(bit12=0),
CHIP_CFG=0x8030(bits2:0=0), SLEEP=0x2810(bit15=0); CSR 0x094 rxc_pin_cnt flies within
1s -> RXC output restored.

## 2026-11-05 (G7 closing: RAW10 UDP stream board-level acceptance PASS)

### Programming rules (explicitly stated by the user, already in project memory)

- Debugging always downloads `.bit` (ftdi_pgm -m jtag, JTAG directly configures the FPGA
  and takes effect immediately, no power cycle needed).
- `.hex` only updates the flash and requires a power cycle afterwards. Several rounds of
  "programming had no effect" (magic case / the probe never appeared) were caused by
  this — the board was running the old netlist all along.

### Proof of the old netlist on the board → 'h92 borrowed-path probe

- reg_apb3 'h092 borrowed path: `{5'h0, pat_dbg_i[8:0], eth_tx_full, eth_tx_free_cnt}`.
  After re-programming the .bit, D92=0x00700fff → raw10_r/pat_en/inf=1 (v2 is really
  running RAW10). On the old netlist the same address read back exactly
  {0,full,free_cnt}, which is indistinguishable from "the probe is all zero" — this is
  how it was detected.
- The independent magic cases ('h83/'h93 etc.) are not on the board; apart from the
  duplicated 'h83 case entries (synthesis takes the first one), the root cause is the
  same (old bit), not a pnr disconnect.

### G7 root cause: the last packet's UDP/IP length fields were full-packet constants (BAD UDP LENGTH)

- All 1788 packets per frame are transmitted on the board (fn continuous, off stepping by
  1450, the 900B last packet online).
- The user's Wireshark capture proves it: the last packet shows
  `[BAD UDP LENGTH 1466 > IP PAYLOAD LENGTH]` → the Windows protocol stack silently
  drops it → the PC UDP socket only ever sees 1787 packets and 0 complete frames.
- Not exposed in the v1 era: in the incrementing mode the packet length was constant
  (PAT_DLEN), so the constant length happened to be correct; only v2's variable-length
  last packet hit the bug. MAC/FIFO flush is ruled out (the OVF/CONT/ifOut counters show
  zero increments).
- Fix: udp_pat_gen_v2.v last packet UDP len=866, IP len=886 (selected by pkt_is_last_w).
- tb_udp_v2 expectation updated in step: 3 frames 8,044,200B byte-for-byte PASS
  (sim/tb_udp_v2.v).
- efx_run compile five stages PASS → program .bit → load ELF → test_raw10_rx.py:
  **295 complete frames / 0 frame loss / 30.00fps / 622.1Mbps / 5 frames pixel-perfect
  comparison OK → G7 PASS**.

### Root cause chain (3 rounds of build iterations)

     L981 becomes an isolated net → the reg_apb3 `'h0A8` read branch is deleted wholesale

     merges them normally; the netlist shows full-width nets with consumers (the
     correct SOT=1 reading on the board corroborates this). Only the "wire declaration +
     assignment" form hits the trap.

- **Instantiating before declaring in the RTL top level = the implicit net trap**: all

  and it reports no error — it only shows up as a branch disappearing / unreachable
  after synthesis.
- Cross-validation means: grep the number of consumers of the probe Q ends in map.v +
